SE Models — Complete Explanations (Q2)

Q2 is ALWAYS a model explanation. For full marks, structure your answer as follows:
  1. Definition (2-3 lines)
  2. Diagram (draw a simple one)
  3. Phases / Steps (numbered with explanation)
  4. Advantages (5+)
  5. Disadvantages (5+)
  6. When to use (2-3 scenarios)
  7. Example (real project)

1. Big Bang Model

The Big Bang model combines a lot of people, money, and resources together with little or no planning, and hopes that the result is great software. Like the Big Bang theory for the universe, the outcome is unpredictable.
Resources + People + Money ↓ [ Lots of Effort ] ↓ ? ? Random Outcome ? ? (great / terrible / nothing)

Key Characteristics

  • Little or no planning
  • Little or no formal testing
  • No specific phases
  • Success depends on luck and team skill
Advantages:
  • Very simple — no process overhead
  • Flexible — developers do whatever they want
  • Good for very small prototypes or experiments
  • Works for solo projects with one skilled developer
  • Low initial cost for management
Disadvantages:
  • Extremely risky — results are unpredictable
  • Cannot handle complex projects
  • No documentation for maintenance
  • Difficult for new team members to join
  • Waste of resources if it fails
When to use: Only for very small, simple, experimental projects where the cost of failure is low, such as student projects or rough prototypes.
Example: A student writing a one-off script to generate a single report. No documentation, no planning, just code and hope.

2. Build & Fix Model

In the Build & Fix model, a product is built without specifications or design effort. The product is delivered to the customer, who reports bugs that are then fixed by the vendor. No formal testing is done.
Build → Deploy → Customer Uses ↓ Reports Bug ↓ Vendor Fixes ↓ (loop continues)

Key Characteristics

  • No testing before release
  • Problems fixed through usage
  • Assumes faithful and patient customers
  • Repaired by the dealer at own cost
  • Bug fixed but process NOT improved
Advantages:
  • Very low upfront cost
  • Customer gets software quickly
  • Simple for developers
  • Works for very small, trivial projects
  • Direct feedback loop with users
Disadvantages:
  • No quality control
  • Customers lose trust quickly
  • Process never improves
  • Costly in the long run (many bug fixes)
  • Not suitable for any professional or large project
  • Reputation damage
When to use: Almost never professionally. Only acceptable for very small programs used by one developer for personal tasks.
Example: An unprofessional vendor releases software and customers call support to report bugs one by one. Bugs are fixed, but the development process stays bad.

3. Waterfall Model — VERY IMPORTANT

The Waterfall Model is a plan-driven, sequential software development model where each phase must be completed and signed off before the next phase begins. It was the first formal software process model and is derived from hardware manufacturing.
[Requirements Analysis] ↓ [System & Software Design] ↓ [Implementation & Unit Testing] ↓ [Integration & System Testing] ↓ [Operation & Maintenance]

The 5 Phases (in detail)

Phase 1: Requirements Analysis and Definition
The system's services, constraints, and goals are established through consultation with system users. These are then defined in detail and serve as a system specification. This phase includes:
  • Feasibility study
  • Requirements analysis
  • Requirements definition
  • Requirements specification
Output: Signed-off Requirements Document (SRS).
Phase 2: System and Software Design
The system design process allocates requirements to hardware or software systems by establishing an overall system architecture. Software design involves identifying fundamental software abstractions and their relationships.
  • System design: partitions requirements to hardware/software
  • Software design: represents software functions in executable-ready form
Output: Design Document (architecture, modules, data structures).
Phase 3: Implementation and Unit Testing
The software design is realized as a set of programs or program units (written new, acquired, or modified). Unit testing verifies each unit meets its specification.
Output: Working code + unit test results.
Phase 4: Integration and System Testing
Individual program units are integrated and tested as a complete system. They are tested against requirements to ensure compliance. After testing, the system is delivered to the customer.
Output: Fully tested, deployed system.
Phase 5: Operation and Maintenance
Normally the LONGEST phase. The system is installed and put into practical use. Maintenance includes:
  • Operation: system in practical use
  • Maintenance: fix errors not found earlier
  • Evolution: add new functions as requirements change
  • Phase out: withdrawn from service
Advantages:
  • Process visibility — clear phases and signed-off documents
  • Quality control — each phase is reviewed before next starts
  • Cost control — early planning helps budgeting
  • Easy to manage — good for contracts and schedules
  • Good documentation — every phase produces docs
  • Works well for large coordinated projects across sites
Disadvantages:
  • Inflexible — cannot easily respond to changing requirements
  • Problems are often discovered late (during testing)
  • Working software is delivered only at the END
  • Not suitable when requirements are unclear
  • Each stage reveals new understanding that may require revising earlier stages (costly rework)
  • Premature freezing of requirements may cause wrong system
  • Design problems circumvented by implementation "tricks"
When to use:
  • Requirements are well-understood and stable
  • Large systems engineering projects across multiple sites
  • Projects needing strong documentation (medical, defense, aerospace)
  • Technology is well-understood, no experimentation needed
Example: Building a payroll system for a government department where tax rules are well-defined and unchanging. All requirements can be documented upfront.

4. V-Model (Verification and Validation)

The V-Model is an extension of the Waterfall model where every development phase is matched with a corresponding testing phase. Development flows down one side of a "V" and testing flows up the other side. Also called the Verification and Validation Model.
Requirements ↔↔↔ Acceptance Testing \ / System Design ↔↔ System Testing \ / Arch Design ↔ Integration Testing \ / Module Design ↔ Unit Testing \ / \ / Coding

Phases (Development side → matched Testing side)

Development Phase (Verification)Testing Phase (Validation)
Requirements AnalysisAcceptance Testing
System DesignSystem Testing
Architectural DesignIntegration Testing
Module DesignUnit Testing
Coding (bottom of V)—

Verification vs Validation

  • Verification: Are we building the product right? (checks documents, plans)
  • Validation: Are we building the right product? (tests against user needs)
Advantages:
  • Testing is planned from the beginning
  • Defects caught early (each phase is verified)
  • Clear deliverables at each stage
  • Disciplined and well-organized
  • Good for critical systems where reliability matters
Disadvantages:
  • Rigid like Waterfall — hard to handle changes
  • No working software until late
  • If requirements change, whole V must be updated
  • Not suitable for small, dynamic projects
  • Expensive due to heavy documentation
When to use:
  • Projects where testing is critical (medical, banking, aerospace)
  • Requirements are stable
  • Compliance with standards required
Example: An airline's flight control system where every requirement must be verifiable and validated through matching tests.

5. Incremental Model

The Incremental Model is a software development method where the model is designed, implemented, and tested incrementally (a little more new is added each time) until the product is finished. It combines elements of the Waterfall model with the iterative philosophy of prototyping.
Requirements ↓ Increment 1: Design → Code → Test → Deliver ↓ Increment 2: Design → Code → Test → Deliver ↓ Increment 3: Design → Code → Test → Deliver ↓ ... until all requirements are met

How It Works

  1. Collect customer's requirements (complete list)
  2. Instead of building entire software at once, take a subset of requirements
  3. Build a module/function from that subset
  4. Deliver it to the customer
  5. Take more requirements, add another module
  6. Continue until the complete system is created
Advantages:
  • Early, partial delivery of useful software
  • Customers see progress and gain value quickly
  • Easier to accommodate changing requirements
  • Customer feedback is easier to obtain
  • Less analysis and documentation to redo compared to Waterfall
  • Backtracking is possible
Disadvantages:
  • Process is not as visible as Waterfall
  • System structure tends to degrade as new increments are added (unless refactoring is done)
  • Managers need regular deliverables to measure progress
  • Large organizations with bureaucratic procedures may struggle
  • Incorporating further changes becomes increasingly difficult
When to use:
  • Requirements are well-defined but partial delivery is beneficial
  • Customer wants early access to core features
  • Risk of changing requirements is moderate
  • Project is too large to complete in one big push
Example: An e-commerce platform where Increment 1 delivers browse + cart, Increment 2 adds payments, Increment 3 adds reviews, Increment 4 adds recommendations.

6. Iterative Model

In the Iterative Model, we start developing software with some initial requirements. When developed, it is reviewed, and if changes are needed, a new version is developed based on those changes. This cycle repeats many times until the final, improved product is obtained.
Initial Requirements ↓ Build Version 1 ↓ Review → Feedback ↓ Build Version 2 (improved) ↓ Review → Feedback ↓ Build Version 3 ... until final product

Key Difference: Iterative vs Incremental

  • Incremental: Each cycle ADDS new features
  • Iterative: Each cycle REFINES the existing product
Advantages:
  • Perfect when requirements are unclear or evolving
  • Continuous improvement based on real user feedback
  • Handles complexity through repeated refinement
  • Good for research and innovation projects
  • Reduces risk by catching issues early
Disadvantages:
  • Hard to manage — unclear when the project ends
  • Can be expensive due to many iterations
  • Requires skilled architects
  • Difficult to estimate time and cost upfront
When to use:
  • Requirements are not fully known
  • Project is complex and needs exploration
  • Innovation is required
  • Product will keep evolving over time
Example: Search Engine (from course material)
A search engine is never "finished." It follows an iterative process to improve accuracy and user experience.
  • Iteration 1: Basic search bar — keyword matching only
  • Iteration 2: Add "ranking" so popular sites appear first
  • Iteration 3: Add "Autocomplete" and "Did you mean?" for typos
  • Iteration 4: Integrate AI to understand question intent
Why it works: It allows developers to react to how billions of people actually use the tool in real-time.

7. Prototype Model

The Prototype Model is a software development approach where a prototype (early version) is built, tested, and reworked based on customer feedback until an acceptable prototype is achieved. It was developed to overcome the shortcomings of the Waterfall model when requirements are unclear.
Communication ↓ Quick Design ↓ Modeling Quick Design ↓ Construction of Prototype ↓ Deployment, Delivery, Feedback ↓ (If not satisfied, refine and repeat) ↓ Final System Development

The 5 Phases of Prototype Model

1. Communication
In this phase, developer and customer meet and discuss the overall objectives of the software. Basic understanding is established.
2. Quick Design
Implemented when requirements are known. Includes only the important aspects: input format, output format, and what the user will see. Focuses on visible aspects rather than detailed internal plans.
3. Modeling Quick Design
Gives a clear idea about software development. Helps developers better understand exact requirements.
4. Construction of Prototype
The prototype is built and evaluated by the customer themselves. Feedback is collected.
5. Deployment, Delivery, Feedback
If the user is not satisfied, the prototype is refined according to new requirements. This process repeats until all user requirements are met. When satisfied, the final system is built based on the final prototype.

Throw-away Prototypes

Prototypes should be discarded after development — they are NOT a good basis for a production system because:
  • Impossible to tune to meet non-functional requirements
  • Prototypes are normally undocumented
  • Structure degrades through rapid change
  • Will not meet normal quality standards
Advantages:
  • Improved system usability
  • Closer match to users' real needs
  • Improved design quality
  • Improved maintainability
  • Reduced development effort in the long run
  • Customer sees and interacts with the system early
Disadvantages:
  • Prototype may not be used the same way as the final system
  • Tester of the prototype may not be typical of real users
  • Training time during prototype evaluation may be insufficient
  • If prototype is slow, users adjust their behavior to avoid slow features
  • Expensive because model may be rebuilt many times
  • Customer may think prototype is the final product
When to use:
  • Requirements are not clear or are evolving
  • User interface design is critical
  • Project has high uncertainty
  • Customer cannot describe exactly what they want
Example: Building a mobile app for a new product. The developer creates a clickable prototype first, shows it to the customer, refines it based on feedback, then builds the real app based on the approved prototype.

8. Agile Model

Agile methods are iterative development approaches that focus on working code rather than design documentation. They aim to deliver working software quickly and evolve it rapidly to meet changing requirements. Agile was created due to dissatisfaction with the heavy overheads of 1980s-90s software methods.

The Agile Manifesto (4 Core Values)

"We are uncovering better ways of developing software by doing it and helping others do it. Through this work we have come to value:"
  1. Individuals and interactions over processes and tools
  2. Working software over comprehensive documentation
  3. Customer collaboration over contract negotiation
  4. Responding to change over following a plan
"That is, while there is value in the items on the right, we value the items on the left more."

The 5 Key Agile Principles

PrincipleDescription
Customer involvementCustomers are closely involved throughout development. They provide and prioritize new requirements and evaluate iterations.
Incremental deliverySoftware is developed in increments with customer specifying what to include in each.
People not processTeam skills are recognized and exploited. Team members develop their own ways of working.
Embrace changeSystem requirements will change. Design the system to accommodate these changes.
Maintain simplicityFocus on simplicity in software and process. Actively eliminate complexity.
Advantages:
  • Fast response to changing requirements
  • Early, frequent delivery of working software
  • High customer involvement and satisfaction
  • Less documentation overhead
  • Better product quality through continuous testing
  • Team morale is higher due to autonomy
Disadvantages:
  • Difficult to keep customer interest throughout
  • Team members must be suited to intense involvement
  • Prioritizing changes difficult with multiple stakeholders
  • Maintaining simplicity requires extra work
  • Contracts are problematic (hard to fix price/scope)
  • Hard to scale to large systems and teams
  • Less documentation can hurt maintenance
When to use:
  • Small or medium-sized product development
  • Custom systems with committed customer involvement
  • Few external rules or regulations constraining the software
  • Requirements are likely to change
Example: A startup building a consumer mobile app. Requirements evolve weekly based on user feedback. Two-week sprints deliver new features rapidly.

9. Scrum Framework — VERY IMPORTANT

Scrum is a general agile method that focuses on managing iterative development rather than specific agile practices. The name comes from rugby where a scrum is a tight formation. It organizes work into fixed-length sprints with specific roles and ceremonies.

The 3 Phases of Scrum

Phase 1: Outline Planning
Establish the general objectives for the project and design the software architecture. No detailed sprint planning yet — just big-picture direction.
Phase 2: Sprint Cycles
A series of short, fixed-length sprints where each cycle develops an increment of the system. This is where most of the work happens.
Phase 3: Project Closure
Wraps up the project, completes required documentation (help frames, user manuals), and assesses lessons learned.

The Sprint Cycle (Detailed)

  1. Sprint duration: Fixed length, normally 2-4 weeks
  2. Product Backlog: The prioritized list of all work to be done on the project
  3. Selection phase: The whole project team works with the customer to select features/functionality to develop during the sprint
  4. Development: Once features are agreed, the team self-organizes to develop them. They are isolated from external distractions.
  5. Daily Scrum: Short daily meeting where team members share progress, problems, and today's plans
  6. Sprint Review: At the end of the sprint, the work is reviewed and presented to stakeholders
  7. Next sprint begins

Key Roles in Scrum

RoleResponsibility
Scrum MasterFacilitator who arranges daily meetings, tracks backlog, records decisions, measures progress, and protects the development team from external distractions.
Product OwnerOwns the product backlog, represents the customer, prioritizes features.
Development TeamSelf-organizing group that builds the software during sprints.
Scrum Benefits:
  • Product broken into manageable, understandable chunks
  • Unstable requirements do not hold up progress
  • Whole team has visibility of everything — improved communication
  • Customers see on-time delivery of increments
  • Gain feedback on how the product works
  • Trust is established between customers and developers
  • Positive culture is created in which everyone expects success
Disadvantages:
  • Requires experienced team
  • Scope creep if Product Owner is weak
  • Daily meetings can frustrate some members
  • Hard to predict total project cost/duration
  • Not ideal for very large distributed teams (needs scaling)
When to use:
  • Small to medium teams (5-9 people typical)
  • Projects where requirements will change
  • Customer is engaged and available
  • Modern product development
Example: Developing a Customer Loyalty Mobile App in Scrum (from course):
  • Sprint 1 (2 weeks): User registration + Login + Database schema
  • Sprint 2 (2 weeks): Points earning from purchases + transaction log
  • Sprint 3 (2 weeks): Reward redemption + promotions
  • Sprint 4 (2 weeks): Referral program + activity tracking
  • Sprint 5 (2 weeks): Testing + deployment
Each sprint has a Scrum Master, assigned developers, status tracking, and priority levels.

10. Plan-driven vs Agile Comparison

AspectPlan-driven (Waterfall, V-Model)Agile (Scrum, XP)
PlanningAll activities planned in advanceIncremental planning, adaptive
RequirementsFrozen early, stableEmbraces changing requirements
DocumentationHeavy, detailed at each phaseLight, working software preferred
Customer involvementLow, mostly at start and endHigh, throughout development
DeliveryOne big delivery at the endFrequent small increments
FlexibilityRigidVery flexible
Risk handlingHigh upfront riskRisk spread across iterations
Team structureHierarchical rolesSelf-organizing teams
Best forLarge, stable projects with regulationsSmall/medium dynamic projects
Contract basisEasy (fixed scope/price)Difficult (evolving scope)
Note: In practice, most real projects include elements of BOTH plan-driven and agile approaches. There are no right or wrong software processes — the best choice depends on the project context.

Exam Tips for Q2 (Model Explanation)

How to write a perfect Q2 answer for FULL marks:
  1. Start with definition (2-3 lines) — shows you know what the model IS
  2. Draw a diagram — even a rough one earns marks. Show phases in order.
  3. List phases/steps with a short explanation of each (1-2 lines each)
  4. Write 4-5 advantages in bullet points
  5. Write 4-5 disadvantages in bullet points
  6. When to use (2-3 scenarios)
  7. Real-world example (1 sentence showing application)
Common Mistakes to Avoid:
  • Don't just write the definition and move on — examiner wants DETAIL
  • Don't forget the diagram — visuals earn marks
  • Don't confuse Iterative with Incremental
  • Don't skip advantages/disadvantages — they're always asked
  • Don't forget "When to use" — shows critical thinking
Most likely Q2 topics (high probability):
  1. Waterfall Model (classic, always asked)
  2. Scrum Framework (hot topic, modern)
  3. Incremental or Iterative (tricky difference)
  4. Prototype Model (clear phases)
  5. V-Model (disciplined approach)
