SE Case Studies — Solved (Q3)

Q3 is ALWAYS a Case Study. You'll be given a scenario (e.g., loyalty app, medical system) and asked to:
  • Write Functional and Non-functional requirements
  • Plan using Scrum with sprints, assignees, priority, status
  • Explain the architecture or process

General Tips for Answering Case Studies

  1. Read the scenario twice — understand what the system should do and who uses it
  2. List all stakeholders (users, admins, owners)
  3. Pick the right model — Scrum is safe for most modern apps
  4. Write 8-12 functional requirements as numbered statements starting with "The system shall..."
  5. Write 6-10 non-functional requirements grouped by category
  6. Draw a Scrum plan table with 4-6 sprints showing assignees, priority, status
  7. Add a brief architecture description (frontend, backend, database)

Functional Requirements — Template

How to phrase them: "The system shall [verb] [object] [condition/detail]"

Examples:
  • The system shall allow users to create an account using email and password.
  • The system shall send an OTP to verify the user's phone number.
  • The system shall calculate total price including tax and discount.
  • The system shall generate a PDF invoice after successful payment.
  • The system shall send an email confirmation within 30 seconds.
Common Functional Requirement Verbs: allow, provide, display, calculate, generate, send, validate, store, retrieve, update, delete, notify, authenticate, process, track, export, import

Case Study 1: Customer Loyalty Mobile App (From Course Material)

Problem Statement:
A retail business seeks to implement a Customer Loyalty Mobile App to improve repeat purchases and customer engagement. The app should allow users to create accounts, earn loyalty points through purchases, redeem rewards, receive personalized promotions, and participate in a referral program to earn bonus points. The app must also maintain complete tracking of all user activities including points earned, redeemed, referred friends, and promotions viewed or claimed.

As a software engineer, develop the app using the Scrum framework, working in multiple sprints to deliver incremental features. Each iteration should clearly outline the responsible person, status, and priority.

Chosen Model: Scrum

Why Scrum?
  • Mobile app development benefits from incremental delivery
  • Customer (retail business) needs rapid feedback on each feature
  • Requirements may evolve (promotions, reward types can change)
  • Team is small, self-organizing
  • Working software delivered every 2 weeks

Functional Requirements

  1. The system shall allow users to create accounts using email, phone number, or social login.
  2. The system shall authenticate users via password + OTP verification.
  3. The system shall display the user's current loyalty points on the home screen.
  4. The system shall add points to the user's account automatically when a purchase is made.
  5. The system shall allow users to redeem points for available rewards.
  6. The system shall display personalized promotions based on user purchase history.
  7. The system shall provide a referral program where users earn bonus points by inviting friends.
  8. The system shall track all user activities: points earned, points redeemed, referrals made, promotions viewed or claimed.
  9. The system shall send notifications about new promotions and reward availability.
  10. The system shall allow users to view their transaction history with dates and point changes.
  11. The system shall enable users to update their profile information.
  12. The system shall provide a customer support chat option.

Non-Functional Requirements

Performance

  • App screens shall load in under 2 seconds on a 4G connection.
  • Points update after a purchase shall reflect within 10 seconds.

Reliability

  • System shall have 99.5% uptime.
  • All transactions shall be logged for recovery in case of failure.

Usability

  • New users shall complete registration in under 3 minutes.
  • App shall support English and Urdu languages.

Security

  • All user passwords shall be hashed using bcrypt.
  • User data shall be encrypted at rest and in transit (HTTPS/TLS).
  • Only authenticated users shall access their loyalty account.
  • Points transactions shall be tamper-proof (audit log).

Scalability

  • System shall support up to 100,000 active users.
  • Database shall handle 1,000 concurrent transactions per second.

Portability

  • App shall run on iOS 14+ and Android 10+.

Scrum Plan (6 Sprints, 2 Weeks Each)

SprintDurationGoal / Backlog ItemsAssigned toPriorityStatus
Sprint 1 2 weeks Project setup: Repository, CI/CD, database schema, authentication module (email + password) Shehroz (Backend), Ali (DB) High Done
Sprint 2 2 weeks User profile, OTP verification, home screen with points display Fatima (Frontend), Shehroz (Backend) High Done
Sprint 3 2 weeks Points earning mechanism, transaction logging, purchase webhook integration Ali (Backend), Bilal (Integration) High In Progress
Sprint 4 2 weeks Reward redemption flow, reward catalog, order confirmation Fatima (Frontend), Shehroz (Backend) Medium To Do
Sprint 5 2 weeks Promotions engine, personalized offers, push notifications Bilal (Integration), Ali (Backend) Medium To Do
Sprint 6 2 weeks Referral program, activity tracking dashboard, final QA & deployment Whole team Low To Do

Architecture

  • Frontend: React Native mobile app (iOS + Android)
  • Backend: Node.js REST API with Express.js
  • Database: PostgreSQL for structured data, Redis for caching
  • Authentication: JWT tokens + OTP via Twilio
  • Notifications: Firebase Cloud Messaging
  • Hosting: AWS (EC2 for API, RDS for database)

Case Study 2: Insulin Pump Control System (From Course Material)

Problem Statement:
An insulin pump is a medical system that simulates the operation of the pancreas. The software controlling this system is an embedded system which collects information from a sensor and controls a pump that delivers a controlled dose of insulin to a user. The system is safety-critical because low blood glucose can lead to brain malfunctioning, coma, and death, while high blood glucose levels can cause long-term eye, kidney, and heart problems.

Chosen Model: V-Model

Why V-Model?
  • Safety-critical system requires testing at every phase
  • Medical systems must comply with strict regulations
  • Requirements are well-understood (medical protocols)
  • Verification and validation are essential

Functional Requirements

  1. The system shall collect blood sugar readings from the sensor every 10 minutes.
  2. The system shall calculate required insulin dosage based on current blood sugar and rate of change.
  3. The system shall send signals to the micro-pump to deliver the calculated insulin dose.
  4. The system shall log every reading, calculation, and dose delivered with timestamps.
  5. The system shall alert the user if blood sugar falls below a safety threshold.
  6. The system shall alert the user if blood sugar rises above a safety threshold.
  7. The system shall prevent over-dosing even if the sensor returns incorrect data.
  8. The system shall allow manual override by medical staff in emergency.
  9. The system shall display current blood sugar level and next scheduled dose.
  10. The system shall shut down the pump if battery falls below 10%.
  11. The system shall export logs for doctors via Bluetooth.

Non-Functional Requirements

Reliability (CRITICAL)

  • System shall have 99.999% uptime (medical grade).
  • Mean Time Between Failures (MTBF) shall be > 5 years.
  • System shall pass all safety tests specified in ISO 13485.

Performance

  • Dosage calculation shall complete in under 100 milliseconds.
  • Sensor reading shall be processed within 1 second.

Safety

  • System shall NEVER deliver more than 10 units of insulin in one dose.
  • Emergency shutoff shall activate within 50 milliseconds of critical reading.
  • Backup power shall sustain operation for at least 1 hour.

Usability

  • Patient shall be able to check status with one button press.
  • Alerts shall be visible, audible, and vibratory.

Maintainability

  • Firmware shall be updatable by authorized medical staff.
  • Error logs shall be accessible via Bluetooth diagnostic tool.

Architecture

  • Hardware: Microsensor (blood sugar), microcontroller, micro-pump, LCD display, buttons
  • Software: Embedded C running on RTOS
  • Communication: Bluetooth Low Energy for logs and firmware updates
  • Storage: Internal flash memory for logs

Case Study 3: Mental Health Patient Management System (MHC-PMS)

Problem Statement:
A patient information system to support mental health care is a medical information system that maintains information about patients suffering from mental health problems and treatments they have received. The MHC-PMS is used in clinics, hospitals, local medical practices, and community centers. It uses a centralized database but can also run on a PC so it may be accessed from sites without secure network connectivity. When offline, local systems download and use local copies of patient records.

Chosen Model: Incremental Model

Why Incremental?
  • Core features can be delivered early (patient records)
  • Additional features added incrementally (appointments, reports)
  • Privacy and security need iterative refinement
  • Requirements are mostly clear but evolving

Functional Requirements

  1. The system shall allow doctors to create and update patient records.
  2. The system shall maintain a history of all patient visits and treatments.
  3. The system shall schedule appointments and send reminders.
  4. The system shall allow doctors to prescribe medications electronically.
  5. The system shall track medication dosage and side effects.
  6. The system shall synchronize local copies with the central database when online.
  7. The system shall allow offline access to patient records at remote clinics.
  8. The system shall generate monthly reports for clinic administrators.
  9. The system shall integrate with external clinical information systems.
  10. The system shall track progress of treatment plans over time.

Non-Functional Requirements

Security & Privacy (CRITICAL)

  • All patient data shall be encrypted at rest and in transit.
  • Access shall be restricted based on role (doctor, nurse, admin).
  • System shall comply with HIPAA and local medical data protection laws.
  • All data access shall be logged (audit trail).

Reliability

  • System shall have 99.9% uptime during clinic hours.
  • Daily backups shall be maintained off-site.

Performance

  • Patient record retrieval shall take less than 2 seconds.
  • Sync with central database shall complete in under 30 seconds.

Portability

  • System shall run on Windows, macOS, and Linux.
  • Web interface shall work on modern browsers.

Usability

  • Doctors shall be trained in under 2 hours.
  • Common tasks shall require 3 clicks or fewer.

Case Study 4: Online Shopping App

Problem Statement:
Develop an online shopping application that allows customers to browse products, add items to a cart, make secure payments, and track their orders. The system should support multiple sellers, product reviews, and a recommendation engine. The business expects up to 50,000 concurrent users during sales events.

Chosen Model: Agile / Scrum

Functional Requirements

  1. The system shall allow users to register and log in with email or social accounts.
  2. The system shall display products with photos, price, description, and reviews.
  3. The system shall allow users to search and filter products by category, price, and ratings.
  4. The system shall allow users to add products to a shopping cart.
  5. The system shall calculate total price including tax and shipping.
  6. The system shall process payments through multiple methods (credit card, JazzCash, Easypaisa).
  7. The system shall generate an order confirmation and email it to the user.
  8. The system shall allow users to track their order status.
  9. The system shall allow users to leave product reviews after purchase.
  10. The system shall provide sellers with a dashboard to manage inventory.
  11. The system shall recommend similar products based on purchase history.
  12. The system shall handle order cancellations and refunds.

Non-Functional Requirements

Performance

  • Pages shall load in less than 2 seconds.
  • Search results shall appear within 1 second.

Scalability

  • System shall support 50,000 concurrent users during sale events.
  • Database shall handle 10,000 transactions per minute.

Reliability

  • System shall have 99.9% uptime.
  • Payment processing shall have 99.99% success rate.

Security

  • All payment data shall be PCI-DSS compliant.
  • User passwords shall be hashed with bcrypt.
  • All communication shall be over HTTPS/TLS.

Usability

  • Mobile responsive design for all screen sizes.
  • Checkout flow shall take 3 steps or fewer.

Portability

  • System shall work on Chrome, Firefox, Safari, Edge.
  • Mobile apps for iOS 14+ and Android 10+.

Case Study 5: University Attendance System

Problem Statement:
Design a web-based university attendance management system that allows teachers to mark attendance, generate reports, and automatically notify students and parents about absences. The system should support 10,000+ students, integrate with the existing student information system, and work on both web and mobile.

Chosen Model: Incremental Model

Functional Requirements

  1. The system shall allow teachers to log in using university credentials.
  2. The system shall display class lists for each teacher.
  3. The system shall allow teachers to mark attendance as Present, Absent, or Late.
  4. The system shall allow students to view their own attendance records.
  5. The system shall generate daily, monthly, and semester attendance reports.
  6. The system shall send SMS/email notifications to parents when a student is absent.
  7. The system shall alert students when their attendance falls below 75%.
  8. The system shall integrate with the student information system for course enrollment.
  9. The system shall allow admins to export attendance data to Excel.
  10. The system shall support QR code based attendance for faster marking.
  11. The system shall maintain a historical record for at least 7 years.

Non-Functional Requirements

Performance

  • Marking attendance shall take less than 5 seconds for a class of 60.
  • Reports shall generate within 10 seconds.

Scalability

  • System shall support 10,000+ students and 500+ teachers.
  • Real-time sync across web and mobile.

Reliability

  • System shall have 99.5% uptime during academic hours.
  • Daily backups shall be kept for 30 days.

Security

  • Role-based access (student, teacher, admin).
  • Attendance records shall not be editable after 24 hours.
  • All data shall be stored on encrypted servers.

Usability

  • Teachers shall complete attendance in 3 taps on mobile.
  • UI shall be available in English and Urdu.

Exam Strategy for Q3 (Case Study)

Time budget for Q3 (assuming ~30 min):
  1. Read & understand (3 min): Read the problem twice. Underline key features.
  2. Pick the model (2 min): Scrum for modern apps, V-Model for safety-critical, Waterfall for stable requirements.
  3. Write 8-12 Functional Requirements (10 min): Start each with "The system shall..."
  4. Write 6-10 Non-Functional Requirements (8 min): Group by category.
  5. Draw Scrum plan table (5 min): 4-6 sprints, assignees, priority, status.
  6. Brief architecture (2 min): Frontend, backend, database, key tech.
What graders LOVE:
  • Clear structure with headings
  • Numbered functional requirements
  • Categorized non-functional requirements
  • A Scrum plan TABLE (not paragraphs)
  • Justification for model choice (1-2 lines)
  • Real-world examples (tech stack names)
Common Mistakes to Avoid:
  • Mixing functional with non-functional (e.g., "login fast" is NOT functional)
  • Vague requirements ("system should be good")
  • Forgetting to assign priority/status in Scrum plan
  • Not explaining WHY you chose a model
  • Writing paragraphs instead of numbered lists
Template to copy for ANY case study:
  1. Problem restatement (1 line)
  2. Chosen model + justification (3-4 lines)
  3. Functional requirements (numbered list of 8-12)
  4. Non-functional requirements (grouped by Performance, Reliability, Security, Usability, Scalability, Portability)
  5. Scrum plan (table with Sprint, Duration, Goal, Assignee, Priority, Status)
  6. Architecture (brief bullet list of frontend/backend/database)
